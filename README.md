# 🏘️ Real Estate Management System - Database Project

פרויקט זה בוצע במסגרת קורס בסיסי נתונים. המערכת מיועדת לניהול מקיף של משרד תיווך נדל"ן, הכולל ניהול נכסים (מגורים ומסחר), סוכנים, לקוחות, פגישות וחוזים.

## 📌 סקירה כללית
המערכת מנהלת את כלל מחזור החיים של עסקת נדל"ן:
- מעקב אחרי נכסים לפי אזורים וערים.
- הפרדה לוגית בין נכסי מגורים לנכסים מסחריים (שימוש בירושה - Inheritance).
- ניהול לוחות זמנים ופגישות בין לקוחות לסוכנים.
- הפקת חוזי מכירה/השכרה וניהול ביקורות על סוכנים.

## 🛠️ טכנולוגיות בשימוש
- **Database:** PostgreSQL (גרסה 18)
- **Management Tool:** pgAdmin 4
- **Data Generation:** Python (Pandas/Faker), Mockaroo
- **Design:** ERDPlus

## 📐 ארכיטקטורת בסיס הנתונים
הפרויקט כולל 11 טבלאות המקושרות ביניהן בקשרי גומלין (Foreign Keys) תוך שמירה על שלמות נתונים (Referential Integrity).

### ישויות מרכזיות:
- **Property:** טבלת האב של הנכסים.
- **Residential / Commercial:** טבלאות ירושה המרחיבות את פרטי הנכס.
- **Agent & Client:** ניהול המשתמשים במערכת.
- **Schedule & Contract:** ניהול האינטראקציות והעסקאות.

## 📊 אכלוס הנתונים (Data Population)
בפרויקט זה יושמו 3 שיטות שונות להזנת נתונים, כדי להדגים גמישות ועבודה עם מאסות של מידע:

1. **Mockaroo (500 רשומות):** שימש לאכלוס טבלאות התשתית (`Area`, `City`, `Agent`, `Client`) במידע דמוי-מציאותי ומגוון.
2. **Python Script (20,000 רשומות):** נכתב סקריפט ייעודי לייצור מאסיבי של נתונים עבור טבלאות ה-`Property` וה-`Schedule`, על מנת לבחון ביצועי שאילתות על בסיס נתונים גדול.
3. **CSV Import:** ייבוא נתונים מרוכז עבור טבלאות הירושה (`Residential`, `Commercial`) דרך ממשק ה-Import של pgAdmin.

## 📂 מבנה המאגר (Repository Structure)
- `/SQL_Scripts`: כולל את הקבצים ליצירת הטבלאות (`create`), מחיקתן (`drop`) ושאילתות לדוגמה (`select`).
- `/Data_Files`: קבצי המקור (CSV ו-SQL של Mockaroo).
- `/Scripts`: קוד הפייתון ששימש ליצירת הנתונים המאסיביים.
- `Backup_File.sql`: גיבוי מלא של בסיס הנתונים (המבנה והנתונים).

## 🚀 הוראות הרצה
1. צור Database חדש ב-pgAdmin בשם `RealEstateDB`.
2. פתח את ה-Query Tool והרץ את הקובץ `SQL_Scripts/createTables.sql`.
3. הרץ את קבצי ה-Insert לפי הסדר (Area -> City -> Agent -> Client -> Property...).
4. (חלופי) ניתן פשוט לבצע **Restore** לקובץ ה-`Backup_File.sql` כדי לקבל את המערכת מוכנה תוך שניות.


שלב ב' - מודל רלציוני ושאילתות (מערכת לניהול נדל"ן)
📌 הערה לבודק: כל צילומי המסך המעידים על הרצת השאילתות, מצב הנתונים לפני ואחרי פעולות DML (Update/Delete), הוכחות הטרנזקציות ושגיאות האילוצים, שמורים ומסודרים בתוך תיקיית stage 2 במאגר זה.

שאילתות SELECT כפולות (השוואת יעילות)
שאילתא 1: מציאת סוכנים עם פגישות מתוכננות בחודש מאי

תיאור: מציגה את שמות הסוכנים שיש להם לפחות פגישה אחת מתוכננת בחודש מאי, לטובת ניהול משאבים בלוח המחוונים.

השוואת יעילות: צורה ב' (EXISTS) יעילה יותר מצורה א' (JOIN + DISTINCT). שימוש ב-EXISTS גורם למנוע החיפוש להפסיק לסרוק ברגע שהוא מוצא התאמה אחת לסוכן, בעוד ש-JOIN מבצע הצלבה מלאה של כל הרשומות ואז נדרש למיין ולהסיר כפילויות באמצעות DISTINCT (פעולה יקרה חישובית).

שאילתא 2: נכסי מגורים עם מרפסת בתל אביב

תיאור: מאתרת רשימת דירות רלוונטיות עבור לקוחות המחפשים נכסים בעלי מאפיין ספציפי בעיר מוגדרת.

השוואת יעילות: צורה ב' (INNER JOIN) יעילה יותר מצורה א' (IN עם Subquery). מנוע ה-PostgreSQL מצטיין באופטימיזציה של פעולות JOIN ובוחר את סדר סריקת הטבלאות המהיר ביותר, בניגוד לתת-שאילתא שלעיתים דורשת חישוב מלא של הרשימה הפנימית לפני ביצוע הסינון.

שאילתא 3: כמות חוזים סגורים לכל סוכן

תיאור: מפיקה את מספר העסקאות שהשלים כל סוכן, לטובת גרף "ביצועי סוכני נדל"ן".

השוואת יעילות: צורה ב' (JOIN + GROUP BY) עדיפה ויעילה משמעותית מצורה א' (Subquery ב-SELECT). בצורה א', מנוע הנתונים נאלץ לבצע את תת-השאילתא מחדש עבור כל שורה ושורה בטבלת הסוכנים (N+1). שימוש ב-GROUP BY מאפשר קריאה אחת רציפה של הנתונים.

שאילתא 4: נכסים ללא תגיות מיוחדות (Amenities)

תיאור: מציאת נכסים שחסר להם מידע תיאורי כדי לתעדף איסוף נתונים על ידי המשרד.

השוואת יעילות: צורה ב' (LEFT JOIN עם IS NULL) עדיפה. שימוש ב-NOT IN (צורה א') עלול לגרום לבעיות ביצועים או אף לתוצאות שגויות לחלוטין אם הרשימה הפנימית מכילה ערכי NULL. ה-LEFT JOIN נחשב לבטוח יותר וממופה טוב יותר לאינדקסים הקיימים.

שאילתות SELECT מורכבות נוספות
שאילתא 5: שליפת פגישות עתידיות (סטטוס מתוכנן), תוך פירוק התאריך ליום, חודש ושנה בנפרד (עבור יומן הפגישות).

שאילתא 6: הצגת דירוג ממוצע לסוכנים שקיבלו יותר מביקורת אחת בלבד.

שאילתא 7: איתור נכסים יוקרתיים (מחירם גבוה מהמחיר הממוצע בעיר שלהם ספציפית), מבוסס תת-שאילתא מתואמת.

שאילתא 8: חישוב סך ההכנסות מחוזים של נכסים מסחריים, מקובץ לפי סוג העסק (Business Type).

פעולות DML (עדכונים ומחיקות)
UPDATE:

עדכון סטטוס פגישות שעבר זמנן ל-'Completed'.

העלאת מחיר ב-5% לכל נכסי המגורים שכוללים מרפסת.

העברת כל הנכסים של סוכנים בעלי דירוג נמוך מ-3 לטיפולו של סוכן ראשי (agent_id = 1).

DELETE:

מחיקת פגישות שבוטלו (Cancelled) לפני יותר משנה, לטובת ניקוי היסטוריה.

מחיקת תגיות שירות (Amenities) שאינן מקושרות לאף נכס קיים.

מחיקת ביקורות סוכנים שאינן מכילות טקסט ממשי (ריקות או רווחים בלבד).

אילוצים (Constraints)
הוספו 3 אילוצים עסקיים למערכת (ALTER TABLE):

chk_min_contract_price: מחיר חוזה סופי חייב להיות לפחות 50,000 ש"ח.

chk_phone_length: מספר הטלפון של לקוח חייב להכיל לפחות 9 תווים.

chk_valid_review_text: ביקורת חייבת להכיל טקסט ממשי ולא יכולה להיות ריקה.

טרנזקציות (Rollback & Commit)
בוצעו ותועדו שתי טרנזקציות:

Rollback: מחיקת כל טבלת הביקורות (AgentReview) ושחזור מיידי שלה באמצעות פקודת Rollback.

Commit: העלאת מחיר של נכס ספציפי ב-10,000 ש"ח, ביצוע Commit ווידוא שהשינוי אכן נשמר במסד הנתונים.
